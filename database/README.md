# База данных

PostgreSQL 17 + pgvector. Инициализация пустой БД SQL-скриптами, без автоматических миграций.
Приложения и интеграционные тесты описаны в [корневом README](../README.md).

- `schema.sql` — базовая структура БД: таблицы, индексы, ограничения, триггеры и представления.
- `import.sql` — разовая загрузка трёх CSV средствами PostgreSQL (`COPY`).
- `application.sql` — расширение для Python-сервисов: durable jobs, chunk RAG, пользовательские
  токены, отчёты и их неизменяемые версии, обсуждения и аудит инструментов.
- `compose.yaml` — запуск БД и хранение данных в Docker volume.
- `df_*.csv` — исходные данные; должны лежать рядом с `compose.yaml`.

## Запуск

Для общего стека БД + embeddings + SearXNG используй
[`../infrastructure/README.md`](../infrastructure/README.md).
Ниже — отдельный запуск только БД из каталога `database`:

```sh
docker compose up -d --wait --wait-timeout 600
```

На **пустом volume** Docker применит `schema.sql`, импортирует CSV через `import.sql`,
затем применит `application.sql`. Все три шага также включены в единый `../infrastructure/compose.yaml`.
Первый запуск дольше обычного: загружается около 1,5 млн строк. При следующих запусках
данные сохраняются, схема и импорт повторно не выполняются.

Подключение по умолчанию:

```text
postgresql://alfa:alfa_dev_password@localhost:5432/alfa_hack
```

Порт опубликован только на `127.0.0.1`. Для изменения параметров можно создать `.env`
рядом с `compose.yaml` и задать `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`,
`POSTGRES_PORT`. Пароль по умолчанию предназначен только для локальной разработки.
Изменение этих переменных не меняет пользователей и пароль уже созданной БД.

## Данные

| CSV | Таблица | Строк |
| --- | --- | ---: |
| `df_Uid_data_hack.csv` | `bank_company_data` | 85 525 |
| `df_Uid_payment_hack.csv` | `bank_payment_edges` | 1 380 585 |
| `df_Fid_Uid_link_hack.csv` | `bank_person_links` | 12 514 |

Из идентификаторов компаний также заполняется `companies`. В `bank_import_batches`
сохраняются имя файла, SHA-256 и количество строк. Каждая исходная строка сохраняется
в `raw_attributes` со всеми колонками, включая не вынесенные в отдельные поля,
пустые строки и исходное написание значений. `source_row_number` — номер записи
с учётом заголовка (первая запись данных — 2).

Валюта, год выручки и период платежей в CSV не заданы и остаются `NULL`.
Значение выручки `1000.0` сохраняется как есть: подтверждения, что это маркер
отсутствующего значения, нет. Прочие таблицы не заполняются выдуманными демоданными.

Посмотреть результат импорта:

```sh
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT dataset, status, row_count FROM bank_import_batches ORDER BY dataset;"'
```

Открыть SQL-консоль:

```sh
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Логи запуска:

```sh
docker compose logs -f db
```

## Интеграционные правила сервисов

Ниже — контракт базовых таблиц. Workflow профилирования, RAG и публикации отчётов теперь
реализован в `../alpha/`; внешний ranker остаётся отдельной интеграцией.
Дополнительные таблицы и ограничения приложения находятся в `application.sql`.

### Профили и пользовательские контексты

- Владелец публикации профиля — **Profiler**: создаёт `company_profiles` в `draft`,
  факты, связи и общие аспекты; вычисляет embeddings через HTTP, сохраняет их,
  привязывает к аспектам, публикует аспекты, затем сам профиль через `UPDATE`.
  `INSERT` профиля сразу в `ready` запрещён. Публикация проверяет наличие общих
  аспектов, готовность всех этих аспектов, единую конфигурацию и пригодность фактов.
- Внешние HTTP/LLM/web-вызовы выполняются вне SQL-транзакций. Создание draft,
  сохранение ответа и публикация — короткие отдельные транзакции. Версии/хеши
  входа проверяются повторно перед привязкой результата, после задержки HTTP-вызова.
- `company_facts` append-only: проверенный кандидат не обновляется. Создай новую
  запись со статусом `usable` и `supersedes_id`, включи её в новый draft-профиль.
- Основания записываются в реальные таблицы связей (`company_profile_facts`,
  `facet_facts`, таблицы целей и т. д.), а не только в JSON-массивы.
  Ready-записи и их основания нельзя дописывать/переписывать в обычном workflow;
  правки требуют новой версии. Это не заменяет проверку авторизации в сервисах.
- Общие и личные цели не смешиваются. Персональные аспекты `scope=user_company`
  создаются после готовности и профиля компании, и конкретного `user_preferences`.
- Пользователь без анкеты: Backend создаёт `app_users`, membership и пустой
  пользовательский контекст; цели при наличии записывает **до** публикации.
  Для ready-предпочтений явно задаётся `published_at`. Это ответственность Backend,
  БД не создаёт пустой контекст автоматически. Корпоративный ranking без пользователя
  допустим; `user_id` без `user_context_id` — нет.

### Embeddings и повторные операции

- `embedding_configs` теперь append-only: **любой UPDATE/DELETE запрещён**, даже
  если конфигурация ещё не использована. Новая модель, revision, шаблон, нормализация
  или другая политика кодирования требуют нового `embedding_config_id` и `config_key`.
  Размерность остаётся 1024. Не смешивай разные конфигурации при поиске.
- Наш [`embedding-service`](../embedding-service/README.md) — stateless HTTP API:
  он **не сохраняет** векторы, не выдаёт ID записей БД и не публикует аспекты.
  Это делает вызывающий Profiler/Parser. Аспекты кодируются как `query`, новости —
  как `document`. Модель/revision/инструкция из ответа должны соответствовать
  выбранной конфигурации; версию подготовки текста также фиксирует клиент.
- Клиент связывает ответ с точным входом: для аспекта — ID контекстов и хеш текста,
  для новости — `article_id`, `content_version` и хеш кодируемого текста.
  HTTP API возвращает векторы в порядке `inputs`, а не идентификаторы задач.
  Гарантия соответствия хеша реальному входу остаётся в адаптере сервиса.
- Для повторов используй уникальные ключи: `(embedding_config_id, encoding_role,
  text_sha256)` у `search_embeddings` и `(article_id, content_version,
  embedding_config_id)` у `news_embeddings`. Запись через `ON CONFLICT DO NOTHING`,
  затем чтение и проверка существующего результата; не `DO UPDATE` append-only записей.
  Повтор публикации ready-записи должен вернуть прежний результат без UPDATE.

### Новости, ранжирование и обратная связь

- Parser сначала согласованно сохраняет `news` и `news_revisions`, коммитит,
  затем запрашивает embedding конкретной ревизии. Изменение текста — новая
  `content_version`, не замена архивной записи. Предусмотри повтор обработки
  ревизий без embedding: успешный commit сам по себе не гарантирует доставку задачи.
- Точный дубль сохраняется с источником и `duplicate_of_id`; retr-rank исключает
  такие записи из кандидатов. Семантическая близость не означает точный дубль,
  а `event_id` — связь события, не произвольный кластер похожих текстов.
  `published_at` — известная дата публикации, иначе NULL; `fetched_at` её не заменяет.
- Retr-rank закрепляет конкретные ready-контексты и embedding-конфигурацию на весь
  запуск, сохраняет кандидатов и основания **до** `completed`. Insight Agent читает
  именно этот запуск и его ревизии, не подставляя «последние» контексты автоматически.
- Frontend логирует фактические показы, не весь список API. Действия связаны
  с `impression_id`; повтор одного действия передаёт тот же `interaction_id`.
  Адаптер использует `ON CONFLICT DO NOTHING` и проверяет прежнее содержимое.
  Непросмотренная карточка не отрицательная метка. Для insight/event сохраняются
  исходные кандидаты в `candidate_refs`; клик не делает все статьи положительными.
- Повторы UID в банковском CSV сохраняются. При сборке профиля разрешай конфликты,
  фиксируй `bank_record_id` и import snapshot; простой JOIN по компании может
  размножить строки. Нормализацию выручки, валюты, периодов и платёжных агрегатов
  выполняй с указанием источника/версии метода, не меняя raw-импорт. Синтетический
  UID не раскрывает реальную компанию; web-факты требуют проверки соответствия.

Готовность PostgreSQL означает готовность соединения/инициализации, но не наличие
ready-профилей или индексированного корпуса нужной конфигурации. API приложений
должен различать эти состояния и возвращать понятное состояние подготовки.

## Остановка и пересоздание

Остановить с сохранением данных:

```sh
docker compose down
```

**Удалить все данные** и создать БД заново по текущей схеме и CSV:

```sh
docker compose down -v
docker compose up -d --wait --wait-timeout 600
```

После изменения `schema.sql`, `import.sql` или CSV для повторного применения нужен
новый пустой volume. Это относится и к новым ограничениям конфигураций/публикации:
простой restart их не добавит. Не запускай весь `schema.sql` поверх заполненной БД.
Если данные важны, сначала сделай backup и согласуй точечное обновление ограничений
вместо удаления volume. Отдельных файлов миграций в репозитории нет. Если первая инициализация завершилась ошибкой, исправь причину
по логам и также пересоздай volume: простой перезапуск не повторяет init-скрипты.
