# Подключение retrieval-ranking

Этот файл описывает существующее подключение нашего сервиса.
Схему общей БД и интерфейсы других модулей он не изменяет.
Запуск и синтетическое демо: [README](../README.md).
HTTP-схема: [openapi.json](openapi.json).
Результаты проверки: [VALIDATION](VALIDATION.md).

## Какие данные читает сервис

Целевая схема — alpha-database commit
`861ea8dde6e84bd1495dae8d9e7e866bf62c3bb8`.
Тестовая копия и её происхождение:
[provenance](../tests/fixtures/schema-provenance.json).

До запроса в общей БД должны быть подготовлены:

- ready company_profiles и company_context_facets выбранной компании;
- совместимые query-векторы в search_embeddings;
- news и текущие news_revisions;
- document-векторы в news_embeddings для vector-канала;
- для персонального запроса — активное company_memberships и ready user_preferences.

Сервис использует одну совместимую embedding-конфигурацию: Qwen3-Embedding-0.6B,
1024 измерения, cosine, normalize=true. Корпоративные и персональные векторы
выбранных аспектов должны иметь тот же embedding_config_id.
text_hash аспекта соответствует text_sha256 query-вектора, encoding_role=query.
Готовые версии публикуются до as_of и не изменяются на месте.

Vector-канал читает текущую content_version. FTS может найти новость без вектора,
но соответствующая ревизия нужна. duplicate_of_id и фильтры дат учитываются
в обоих каналах; новости без даты по умолчанию исключены.
БД выбирает кандидатов; весь корпус новостей в Python не загружается.

Сервис записывает только ranking_runs и ranking_items.
Он не создаёт профили, не парсит новости, не рассчитывает эмбеддинги
и не выполняет миграции общей БД. fixtures/schema.sql используется только
для собственной изолированной тестовой БД.

## Вызов

```sh
curl --fail-with-body http://127.0.0.1:8002/ready
curl --fail-with-body http://127.0.0.1:8002/rank \
  -H 'Content-Type: application/json' \
  -d '{"company_id":"<company_id>","top_k":10}'
```

Корпоративный запрос не передаёт user_id и user_context_id.
Персональный передаёт user_id, при необходимости — user_context_id.
Готовые персональные аспекты необязательны, но ready preferences обязательны.
При их отсутствии сервис возвращает ошибку, без молчаливой смены режима.

Можно закрепить profile_id, user_context_id, embedding_config_id
и передать as_of / published_after. Даты содержат часовой пояс,
будущий as_of запрещён. Явно указанные версии не заменяются новыми.

Ответ содержит ranking_run_id, выбранные версии, candidate_count и items.
У новости есть article_id, content_version, title, text, description,
source_name, source_url, published_at, rank, score, retrieval_hits
и диагностика document_truncated / token_count.
Эмбеддинги в ответ не включаются.

score = logit(yes) - logit(no), не вероятность.
Отрицательные значения допустимы. Порядок — score убывает,
при равенстве article_id возрастает. Порог релевантности не откалиброван.
Возвращается до top_k новостей; пустой пул даёт items=[].
Все оценки сохраняются, rank за пределами выдачи равен NULL.

## Ошибки и ожидание

| HTTP | Значение |
| --- | --- |
| 403 | Нет активного членства пользователя в компании |
| 409 | Нет совместимого ready-контекста или превышен бюджет аспектов |
| 422 | Неверные параметры, даты или лимиты |
| 429 | CPU-worker занят; Retry-After: 1 |
| 503 | Ошибка доступа к БД или выполнения модели |

Ошибки сервиса: `{"error":{"code":"...","message":"..."}}`.
Ошибки Pydantic: `{"detail":[...]}`.
Статический OpenAPI автоматически описывает 200/422;
остальные статусы перечислены выше.

API внутреннее, аутентификация выполняется вызывающим приложением.
Оно связывает user_id с авторизованным пользователем.
Проверка membership сама по себе не подтверждает личность.
POST создаёт новый ranking_run; идемпотентность повторов не заявлена.

Один запрос ранжирования исполняется одновременно.
top_k ограничивает ответ, а не количество оцениваемых кандидатов.
На проверенном CPU запрос на 37 кандидатов занимал около 177 секунд.
Таймаут вызывающего backend/proxy должен учитывать такие задержки;
для 100 кандидатов время отдельно не измерено.

.env.example выбирает i2, лимит пары 2048, контекста 512, batch=2 и 4 потока.
Один API-worker. Модель загружается до готовности /ready;
при первом запуске требуется скачивание весов.
В Docker используется имя БД внутри общей сети, а не localhost.
