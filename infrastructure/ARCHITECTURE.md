# Alpha — персонализированная бизнес-аналитика

Два собственных многошаговых агента, Python/FastAPI backend и отдельный Python tool-gateway.
Новости и банковские CSV используются из существующих Parser/PostgreSQL. Ранжировщик — внешняя
интеграция другого участника команды, **в этом проекте не реализован и не подменён скрытым mock**.

## Архитектура

```text
UI → Backend → анкета / закрытое хранилище файлов / очередь PostgreSQL
                   ↓
         OCR + извлечение + chunk RAG
                   ↓
Company-user-profiler → факты + версия компании + личный контекст + query facets
                   ↓
Backend scheduler → внешний Ranker → POST Insight Agent /runs
                                       ↓
                plan → tools → synthesis → validation → review → repair
                                       ↓
                        версии отчёта / карточки / claims / источники

Mock bank publication API → cursor polling → PDF/OCR → bank analytics RAG
Parser → news + immutable revisions → отдельный chunk indexer → news RAG
Оба агента → Tool Gateway → общие Python-адаптеры PostgreSQL / SearXNG / web fetch
```

Общий пакет `../service-common/agent_common/` содержит контракты и переиспользуемый runtime.
Предметная реализация находится в отдельных соседних проектах: `backend`, `company-user-profiler`,
`insight-agent`, `tool-gateway`, `bank-materials-source`. Сетевые границы сервисов сохраняются.
Агенты не обходят gateway при вызове инструментов. Запись результатов выполняется сервисным
кодом после проверок, без инструмента произвольного SQL для LLM.

## Запуск

**Точка входа — текущая папка [`infrastructure/`](README.md).**
Используются соседние локальные проекты без GitHub. Для запуска нужна вся локальная раскладка,
описанная в README, а не только эта папка.

Требуется Docker Engine с Compose **2.20+** (`include`), доступ к разрешённому LLM endpoint,
интернет для первоначальной загрузки embedding-модели и внешнего поиска. OCR работает на CPU.
Рекомендуется 12–16 ГБ RAM для полного стека; фактическое потребление зависит от документов.

```bash
# Находясь в infrastructure/
cp .env.example .env
# Заполнить три разных секрета, OPENAI_API_KEY и проверить OPENAI_BASE_URL.
# Для каждого секрета: python -c 'import secrets; print(secrets.token_urlsafe(32))'
docker compose up -d --build --wait --wait-timeout 1200
```

Если меняете PostgreSQL user/password/database, согласованно измените `DATABASE_URL`.
Не запускайте одновременно отдельные compose из `database/`, `embedding-service/` или `parser/`:
единый `infrastructure/compose.yaml` уже включает инфраструктуру, парсер и приложения.
Все команды `docker compose` в этом README выполняются из `infrastructure/`.

Схема применяется в порядке `schema.sql` → `import.sql` → `application.sql` только на пустой БД.
Если остался старый **ненужный** volume, после явной проверки его можно удалить:

```bash
docker compose down -v  # УДАЛЯЕТ БД, загруженные документы и каталог mock-источника!
docker compose up -d --build --wait --wait-timeout 1200
```

Нужные данные сначала сохраните. Автоматической миграции старой заполненной БД нет.

| Сервис | API / Swagger с хоста |
|---|---|
| Frontend | http://localhost:8092/ |
| Backend | http://localhost:8092/admin/docs (API: `/api/*`) |
| Tool gateway | http://localhost:8090/docs |
| Company-user-profiler | http://localhost:8093/docs |
| Insight-agent | http://localhost:8094/docs |
| Моделируемый источник банка | http://localhost:8091/docs |
| SearXNG | http://localhost:8080 |
| Embedding-service | http://localhost:8001/docs |

Внутри Docker используйте имена сервисов и порт 8000 (SearXNG: 8080, DB: 5432).
Приложения публикуются только на loopback; перед публичным размещением нужен TLS reverse proxy.

## Сквозной сценарий

Пути Backend ниже указаны относительно `http://localhost:8092/api`:
например, `POST /admin/demo` означает `POST http://localhost:8092/api/admin/demo`.
У остальных сервисов (gateway, агенты) префикс `/api` не добавляется.

### 1. Создать вымышленную компанию и пользователя

`POST /admin/demo` в Backend, `Authorization: Bearer <ADMIN_TOKEN>`:

```json
{"synthetic_company_id":"U_67","fictional_name":"Демо Компьютерные Системы","display_name":"Анна"}
```

Компания должна существовать в импортированных CSV. Ответ содержит `user_id`, `company_id`
и пользовательский `token` (показывается только при создании). Это явное **демо-сопоставление**,
не установление личности обезличенной организации. Для разных ролей создайте отдельных пользователей.
Во всех пользовательских запросах используйте `Authorization: Bearer <token>`.
В продакшене этот provisioning заменяется корпоративной авторизацией; demo endpoint не SSO.

### 2. Документы и короткая анкета

- `POST /companies/U_67/documents`: multipart `file`, необязательный `title`.
- `POST /companies/U_67/onboarding`:

```json
{"role":"Финансовый директор","responsibilities":["Финансы"],"goals":["Контролировать стоимость финансирования"],"note":""}
```

Загрузка возвращает `document_id` и `job_id`; статус и явный повтор доступны через API заданий.
Поддерживаются PDF, DOCX, XLSX, PNG/JPEG/TIFF/WEBP. Лимит файла 64 МиБ (один банковский PDF
из исходного комплекта больше 25 МиБ). PDF без текстового слоя и сканы идут через Tesseract `rus+eng`.
Есть ограничения страниц, разрешения, распакованного архива и времени subprocess.
XLSX читается без исполнения формул, с сохранением листа/строки и заголовков; значения формул —
только сохранённый кэш, который может отсутствовать. DOCX сохраняет координаты абзацев/таблиц,
но не гарантирует исходную печатную пагинацию и сложную вёрстку.

- `GET /companies/U_67/documents`: статус/ошибка извлечения.
- `GET /jobs/{job_id}`: статус профилирования.
- `POST /jobs/{job_id}/retry`: явный повтор принадлежащего пользователю failed-задания.
- `GET /companies/U_67/context`: опубликованные версии профиля и личного контекста.
- Если в профиле есть `clarification`, ответьте через `POST /companies/U_67/clarifications`
  с `{"question":"...","answer":"..."}`. Это явно общая информация о компании, доступная её
  участникам, не личная цель. Ответ сохраняется как reported-источник, запускает новую версию профиля.

Профиль компании не содержит личные цели. Query facets используют ту же embedding-конфигурацию,
что и Parser/Ranker. Персональные аспекты создаются отдельно после публикации обоих контекстов.

### 3. Получение банковских материалов

Девять PDF из `материалы от банка из пдф/` — только seed моделируемого независимого источника.
Основной сервис **не читает эту папку**: он опрашивает `GET /materials?cursor=...`, скачивает
конкретную версию по API, проверяет SHA-256 и создаёт durable extraction job до продвижения cursor.
Новые материалы можно публиковать без перезапуска через `POST http://localhost:8091/materials`
с `ADMIN_TOKEN`, multipart:

- `file`: PDF;
- `title`;
- `external_id`: необязательно; тот же ID создаёт следующую версию материала;
- `published_at`: необязательное реальное время публикации с часовым поясом.

Версии и исходные файлы сохраняются. Дата скачивания **не подменяет дату публикации**.
Для seed дата не выводится из имени файла или PDF CreationDate: она неизвестна, пока не задана
достоверными метаданными. Поэтому агент обязан отмечать ограничение актуальности таких источников.
Публикация нового материала не означает, что старый обзор становится новым прогнозом.

### 4. Отчёт и интеграция Ranker

`POST /companies/U_67/reports` с `{"request_id":"<новый UUID>"}` создаёт отчёт по запросу.
Ответ содержит `report` и `ranking_request`. Без готового профиля возвращается `awaiting_profile`;
без подключённого ranker — ожидание интеграции, а не выдуманная аналитика.

Установите `RANKER_URL` на HTTP endpoint внешнего ranker. Backend отправляет с `INTERNAL_TOKEN`:

```json
{
  "request_id":"...","report_id":"...","company_id":"U_67","user_id":"...",
  "profile_id":"...","user_context_id":"...",
  "published_after":"2026-10-19T08:00:00+03:00","as_of":"2026-10-26T08:00:00+03:00",
  "callback_url":"http://insight-agent:8000/runs"
}
```

Ranker должен надёжно сохранить задание до подтверждения приёма HTTP 2xx, идемпотентно
обрабатывать повторный `request_id` и повторять callback при сетевых сбоях. После ограниченной
серии неудачных отправок Backend автоматически создаёт новую серию через 15 минут, сохраняя
исходный `request_id` и историю попыток. Отсутствие настройки ranker не блокирует отправку
после её появления. Ranker сам вызывает Insight Agent:

```http
POST http://insight-agent:8000/runs
Authorization: Bearer <INTERNAL_TOKEN>
```

```json
{"request_id":"<ranking_request.request_id>","ranking_run_id":"<completed ranking run UUID>"}
```

Временный контракт до реализации записи ranker в БД:

```json
{"request_id":"<ranking_request.request_id>","article_ids":["<существующий article_id>"]}
```

Ровно один вариант. На приёме ID закрепляются ревизии новостей. Повтор callback не заменяет
ревизии. Для ranking run проверяются компания, пользователь, версии контекста и временное окно.
Цитирование primary-новостей проверяется по паре `(article_id, content_version)` как в агенте,
так и при публикации в БД: новая редакция статьи не подменяет закреплённую.
Присылать произвольный текст статьи без сохранённого источника нельзя. Пустой список допустим:
агент должен честно сообщить об отсутствии обоснованных карточек.

Проверить ожидающие запросы: `GET /reports/{report_id}/ranking-requests` (Backend, user token).
Для ручной проверки до подключения ranker возьмите ID из БД и отправьте временный callback
с внутренним токеном. **Это ручной тест контракта, не реализованный ranking.**

### 5. Просмотр и вопросы

- `GET /companies/{company_id}/reports`: список, краткие сводки и latest published version.
- `GET /reports/{id}`: карточки с механизмом влияния, действием для роли, claims и источниками.
- `GET /reports/{id}?version=1`: историческая версия.
- `GET /reports/{id}/versions`: история и изменения.
- `POST /reports/{id}/questions`: `{"request_id":"<UUID>","question":"Почему это важно для нас?"}`.
- `GET /reports/{id}/discussions`: ответы с источниками; каждый вопрос закрепляет версию отчёта.
- `GET /documents/{id}/content`: защищённое скачивание первоисточника.

API готов для раскрывающихся карточек. Отдельный frontend Альфа-Бизнеса в эту реализацию не входит.

## Понедельник 08:00 и уточнения

Часовой пояс — `Europe/Moscow`. Окно новостей — **[прошлый понедельник 08:00, текущий понедельник
08:00)**, а не календарная неделя. Подготовка начинается за три часа. Для запуска по запросу —
последние семь суток на момент создания. Даты уже созданного отчёта никогда не сдвигаются.

Исторические новости и банковская аналитика могут использоваться как основания; не как свежие
события. Отбор primary Top-K требует известную дату публикации внутри фиксированного окна.

Парсер повторно просматривает все доступные публикации за семь дней. Новые статьи/ревизии,
завершённая индексация материалов банка или новая версия контекста меняют fingerprint входа:
Backend создаёт новый ranking request, и ranker повторно вызывает агент. Отчёт получает новую
версию, предыдущие карточки и основания остаются неизменяемыми. Если после повторного ranking
выбранные ревизии, контексты и набор банковских материалов не изменились, готовая версия
переиспользуется без нового LLM-вызова. История AI-выводов не является
первичным доказательством. Уточнения автоматически отслеживаются для отчётов последних 14 дней.

К 08:00 публикуется доступная аналитическая версия. Если анализ вообще не завершился, scheduler
публикует **явное уведомление о неполноте без фиктивных карточек**, затем уточняет результат.
Это не выдаётся за готовую проверенную аналитику. Полный отказ сервера/БД не позволяет физически
гарантировать доступность к сроку; после восстановления восстанавливается последний пропущенный
недельный запуск. Для более строгого SLA нужны HA, резервные workers и внешний мониторинг.

Скользящий семидневный опрос не гарантирует восстановление любой старой публикации:
если источник вернул материал уже после выхода его даты из окна или не показывает его в RSS,
нужен отдельный backfill/исторический API. Универсальная durable очередь неизвестных URL здесь
не реализована. Новостной архив не создаётся задним числом автоматически.

## RAG, агентная логика и безопасность

- Article-level embeddings остаются для внешнего ranker. `rag_chunks` индексирует точные ревизии
  и фрагменты документов отдельно. Дата публикации закрепляется в `news_revisions`, отдельно
  от даты получения. Исходные документы компании доступны агенту в составе закреплённого профиля,
  а не автоматически из последних загрузок. Позднее уточнение контекста отмечается в отчёте.
  Консервативный размер — до 1200 символов с перекрытием 150;
  это не обещание фиксированного количества токенов. Локаторы сохраняются для цитат.
- Поиск: PostgreSQL Russian FTS + cosine pgvector → RRF → до трёх фрагментов одного материала.
  При недоступности embeddings остаётся FTS с явным предупреждением. Query/chunk конфигурации
  проверяются; векторы разных конфигураций не смешиваются.
- Собственная агентная логика: план → инструменты → структурированный черновик → проверка схемы,
  прав и ссылок → отдельный LLM review → исправление или новый поиск. Число шагов, время,
  токены и размер контекста ограничены. Лимит контекста считается в UTF-8 байтах — это
  консервативный guard, а не точный tokenizer LLM. Токенный бюджет учитывается по ответам API;
  при сетевых сбоях он не заменяет учёт фактической стоимости на стороне провайдера. Фактологическая истинность не гарантируется одной структурной проверкой.
- Company facts содержат точные цитаты и источники. Каждый инсайт связан с конкретным фактом
  профиля и primary новостью. Позиция банка допускается только с `bank_analytics` источниками.
- `agent_runs`, `agent_steps`, `tool_audit` сохраняют краткую трассу, не скрытую цепочку рассуждений.
- Пользовательские токены хранятся как SHA-256, доступ проверяется по активному membership.
  Отчёты и обсуждения принадлежат конкретному пользователю, документы компании доступны её членам.
- Внутренние API требуют отдельный service token. Он предполагает доверенную сеть и сервисы;
  для production нужны раздельные credentials/mTLS, ротация, полноценный SSO и сетевые политики.
- LLM не получает SQL или произвольные права записи. Источники считаются недоверенными данными;
  инструкции внутри документов не должны менять системную политику. Это снижает, но не устраняет
  prompt-injection риск. Public search имеет эвристический запрет идентификаторов, не полноценный DLP.
- Web fetch: только HTTPS/443, проверка и pinning публичного DNS, повторная проверка redirect,
  TLS verification, лимиты тела/таймаутов. Сниппеты SearXNG — discovery, не доказательства.
- OCR/парсинг — ограниченный subprocess в непривилегированном контейнере. Для production его
  стоит вынести в отдельную сетевую песочницу с отдельными credentials и антивирусным сканированием.

## Проверки и наблюдаемость

```bash
uv sync --group dev
uv run pytest -q                # unit tests; DB tests explicitly skipped without opt-in
uv run ruff check tests ../service-common/agent_common ../backend/backend_service \
  ../company-user-profiler/profiler_service ../insight-agent/insight_service \
  ../tool-gateway/tool_gateway_service ../bank-materials-source/bank_source_service
# Только отдельная тестовая БД PostgreSQL с установленным pgvector:
TEST_DATABASE_URL=postgresql://... uv run pytest -q
```

DB tests используют временные изолированные схемы, проверяют реальную SQL-публикацию профиля,
источники, tenant isolation, leases, immutable history и уточнение отчёта после поздней новости.
LLM и embeddings в этих тестах детерминированно заменены — качество реальной модели и OCR
на банковских сканах требуют отдельного smoke/evaluation прогона.

`GET /admin/metrics` с ADMIN_TOKEN: статусы заданий/документов, ошибки агентов, расход токенов,
количество deadline-уведомлений. Логи: `docker compose logs -f backend-worker document-worker profiler-worker insight-worker`.
Обработка документов вынесена в отдельную очередь worker-роли, чтобы OCR не занимал все
слоты отправки заданий ranker и фоновой индексации.
Качество дополнительно оценивайте экспертной разметкой: корректность источников, причинной связи,
атрибуции банка, различие рекомендаций для ролей, полезность, latency и стоимость.

Сторонние компоненты и моделируемые интеграции: [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).
